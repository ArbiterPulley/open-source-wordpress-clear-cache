Why every page of your WordPress site is slow

A site that is slow everywhere is a different problem from a site with one slow page. Four measurements separate the usual causes: time to first byte, HTML size, image weight, and query count. Thistle Press Cache records the last three for you and caches the first out of existence once pages are warm.

Measurement 4 — the database

Revisions, expired transients, orphaned metadata and spam comments all sit in the same tables every page reads. On a five-year-old site that is commonly 30–60% of the database, and cleaning it shortens every query that touches those tables.

Measurement 2 and 3 — HTML and images

An uncached WordPress page is often 60–120 KB of HTML, most of it whitespace, inline styles and plugin markup. Minification and lazy loading cut the bytes the browser must parse before it can paint. Images are usually the larger number: a 4000-pixel hero scaled to 1200 is four times the bytes for no visible gain, and converting to WebP or AVIF removes another 25–50%.

Measurement 1 — time to first byte

Above roughly 600 ms on a cached page, the server is the problem: no object cache, an overloaded host, or PHP doing work per request that should be done once. A page cache turns this into a file read, which is the single largest win available on shared hosting.

The order to fix them in

Cache first, because it removes the render cost entirely. Then HTML size, then images, then the database. Doing them in the other order produces a faster page that is still rendered on every request.

Three numbers on the dashboard answer it: hit rate, bytes saved per request, and average generate time. A hit rate that climbs over a day of real traffic means the cache covers the pages people visit. Bytes saved moving means minification and image conversion are reaching the response. Generate time is what a visitor would have waited without the cache — if it does not drop, the pages are not being served from it.

Then confirm from outside: open the site in a private window, reload twice, and compare the server timing header before and after. A cached response is a few milliseconds of server work; an uncached one is your theme plus every active plugin. If the second reload is not markedly faster, an exclusion is swallowing the request.

Who this is for

Anyone who has installed a caching plugin, seen a green score, and still had a slow site. Thistle Press Cache is aimed at the diagnosis as much as the fix: cache, output size, media and the database are counted separately, so the next thing to change is not a guess. It is not aimed at sites that need an edge network or a support contract.

What it does not do

No CDN. No image CDN. No edge computing, no page builder, no backup, no security firewall. Thistle Press Cache does not rewrite your theme, does not inject a dashboard banner asking for a review, and does not phone home unless the administrator ticks the box on the dashboard. If a feature needs a remote service to work, it does not belong in a cache plugin.

Frequently asked

The dashboard shows a high hit rate but the site feels slow — why?

A hit rate only covers pages that were cached. Check whether the slow page is excluded, whether it is a logged-in view, and whether images on it are the problem.

Does caching help admin pages?

No. Logged-in requests bypass the cache by design; admin slowness is usually queries or host CPU.

How long should a cached page take?

On a modest server, 50–200 ms of server time. If it is much more, the cache is missing the request.
